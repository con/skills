# Align a project with STAMPED

Use [assess-stamped](../assess-stamped/SKILL.md) for the profile, pinned sources and evidence vocabulary.
Reuse an assessment only when target revision, relevant working state and scope still match.
If the sibling is missing, materialize it from the selected collection revision through the project's installation method; do not reconstruct an assessment from memory.

## Choose a proportionate change

Inventory the existing harness: agent instructions, constitution, contributor guidance and project skills.
Work in the files the project's tools already read; avoid duplicate instructions or editing both ends of a symlink.
Resolve the harness choice only if it is genuinely unknown.

For each important gap, identify consequence, smallest effective fix, and alternatives where a meaningful tradeoff exists.
Use the project's tools first.
Keep scientific-method changes distinct from research-object improvements; a provenance fix cannot validate a scientific claim.

Follow the user's requested scope:

- **Advice only:** deliver proposed changes and tradeoffs.
- **Harness alignment:** show the concise proposed standing instructions; apply them within existing authorization, otherwise obtain agreement before changing standing behavior.
- **Implementation:** complete authorized, reversible fixes and verify them.
  Ask only when a new choice changes scope, cost, access or publication; reuse earlier decisions.

## Write useful standing instructions

One short section, updated in place:

- STAMPED source/assessment pointer and goal-specific emphasis.
- Actual code/data/environment/execution/provenance mechanisms.
- Only the recurring behaviors this project needs: component boundaries, dependency updates, recorded execution, validation and retrieval.

Prefer executable entry points and checks over growing instructions.
Match the user's workflow; do not require every project to adopt a particular package manager, recorder or directory tree.
Materialize missing declared dependencies rather than treating ordinary installation as a terminal failure.

## Verify and hand off

Check changed behavior at the smallest useful scale.
Reassess changed properties against the same checklist pin, retaining before/after object identities, observed outcomes and unresolved gaps.
Within an implementation request, complete that reassessment rather than merely offering it.

Record remaining chosen work in the project's existing tracker or final handoff.
Do not create issues or publish changes without the required authorization.
Stop at the requested scope or a concrete unresolved barrier; planned fixes never count as completed evidence.
