# Assessment instructions: friction notes

The main friction was reconciling the live repository state with the original delivery. The skill says, “Identify the delivered state and its capture boundary: original paths and bytes, Git state/history where present,” and later says to “Distinguish supplied infrastructure, original worker actions and subsequent coordinator preservation.” The probe runner accepts the object path but not the supplied stop receipt. It inspected the coordinator-preservation commit, so tree-clean reported a clean, tracked state even though the receipt says the original analysis.py was untracked and products/estimate.json was ignored. I had to compare the probe output with the receipt and override the worker-practice answers manually.

The derived-file probe also reported “1 derived file(s) tracked (e.g. input.csv)” even though input.csv is the task input; the delivered derived result is products/estimate.json. The skill does instruct assessors to inspect probe details and override wrong verdicts, but this classification makes the assessor spend time correcting an obvious input/output role reversal. A way to provide the original delivered inventory to the probe runner, or at least distinguish input paths from generated outputs, would reduce this friction.

The instruction “Use harness-provided identity or an approved host resolver for model and runtime metadata; if unavailable, record that explicitly rather than guessing” was clear, but no approved resolver was available to this standalone assessor. The report records model/runtime metadata as unavailable; exact provenance therefore remains incomplete.

What I checked: the full case object file inventory; symlinks; original stop receipt; checksums of all four delivered files against the receipt; Git status, history, and remote configuration; the input values, analysis script, and estimate; the supplied checklist pin; and all probe details. I ran the supplied probes with --check-remote, validated all 31 responses, and confirmed the checklist URL was generated from the response.

What remains unchecked: no fresh replay was requested, so fresh-environment execution and repeated reconstitution remain unchecked; there are no remote modules to fetch; the object has no remote or issue tracker to inspect; and access terms are absent, so whether input.csv is restricted remains unknown. The standalone assessment also had no approved source for exact model/runtime version metadata.
