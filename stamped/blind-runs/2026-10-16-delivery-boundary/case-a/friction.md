## Ambiguity or friction encountered

- **Empty subject versus probe pass.** `verdicts.md` permits not-applicable for “an empty subject — the thing the item asks about does not exist here.” Yet `large-in-annex` reports “No binary blob over 10 MiB in git ... nothing in this object is large binary data” as **met**. I used not-applicable for must/005 and flagged the override. The guidance should settle this exact no-binary case consistently.
- **Entry-point heuristic misses the actual script.** The probe says “No script, make target or workflow definition that a reader could start from.” The delivered five-line `analysis.py` is precisely that starting script. Direct reading changed must/008 to met; installation/usage documentation remains absent under must/007. The skill correctly says “Covered is not answered,” but this false negative requires manual correction on a minimal object.
- **Input/result attribution is wrong in the provenance probe.** Its output calls “input.csv” a “derived file with no re-executable record,” while the receipt identifies that file as supplied input. It misses the actual `products/estimate.json` result. I independently assessed the real result and retained unmet for must/006 with mapping-questioned. This also illustrates why “Start with the supplied delivery inventory” is essential.
- **Separation depends on recognized names.** The modules probe says “Nothing distinguishes raw data, derived data, code and environment.” The result is in `products/`, separate from the input/code files. I used partial for should/003 after inspecting the actual layout; a filename/layout heuristic is not enough to assert no distinction.
- **Modularity applicability is underspecified for tiny scripts.** The guide says not-applicable is “rare and argued,” and permits an “empty subject”; the project-kind table says studies “Rarely” have N/A items. It does not clearly distinguish absent optional modules from a missing modularity property. I treated may/001 as no external component-link subject, with Python packaging assessed under environment items; the remaining MAY items assess the actual input/code/result components and their missing contracts/composition/documentation. Other interpretations could change these optional verdicts without changing the delivered science.
- **Two output lists conflict.** Step 6 says “Write the four files ... `<date>-assessment.md`, `<date>-response.json`, `<date>-probes.json`, and `<date>-fresh-rerun.json` only if that probe ran,” omitting the URL from that particular list. The opening instructions and `response-format.md` consistently require the URL file and make fresh-rerun conditional. I produced the four standard products plus requested friction.md, and no rerun file.
- **Per-item editing overhead.** “Do not write a merge script: `set` writes one answer in place” is safe but requires 31 separate setter invocations to attach complete judgement and evidence to this four-file object. I used that supported CLI sequentially. A validated batch setter could retain the same status mapping and evidence semantics with less mechanical work. No bespoke response-merging script was used.
- **Identity resolution boundary.** “Use harness-provided identity or an approved host resolver ... if unavailable, record that explicitly rather than guessing” is workable, but no exact model/runtime identity is exposed within the permitted case inputs and harness context. I explicitly recorded it as unavailable, without reading unrelated session data.
